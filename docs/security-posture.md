# Security posture — standing credentials on the anchor

This is the anchor repo's RT-1 standing-credential inventory: what long-lived credentials the module can place on a box, where they live, and what blast radius a compromised anchor gives. The trustee framing that this inventory feeds is the RT-1 security-trust-model note (pcad.it-infra `research/2026-09-13-r6-security-trustmodel`).

## Default posture

The module provisions **no SSH access and no write-capable standing credentials for the anchor's infrastructure** — inbound or outbound. The one credential with a write surface is the ntfy publish token used by the alerting plane (row 2): it can publish to the tenant's notification topic, and nothing else. Nobody logs into the anchor: every change arrives through a per-run approved dispatch (the runner is the admin path), and the netcup device-flow token dies with the runner. Re-entry after the root lock is per-event; rescue mode stays the last resort and disables the netcup firewall (any rescue boot → rotate tang keys).

## Prebuilt provider binary in plan/apply (temporary — issue #218, upstream PR #47)

`provision.yml` carries one deliberate exception to the "everything the run executes comes from the lock file" rule: an apply-only step stages a **prebuilt netcup provider** (the empty-array-as-map fix, upstream issue rixlhq/terraform-provider-netcup#46 / PR #47) and points OpenTofu at it through `dev_overrides`.

- **It is not covered by `.terraform.lock.hcl`.** `dev_overrides` bypasses the lock for plan/apply, so the committed hashes vouch for what `tofu init` installs — which plan/apply then does not use.
- **Its integrity rests on two things:** the sha256 pinned in the step (`PROVIDER_SHA256`, verified before use, fail-closed) and its provenance — the release tag sits on upstream `v1.2.1` + one fix commit, and the binary stamps that commit (`go version -m` → `vcs.revision`, `vcs.modified=false`). Both checks are recorded in the step comment.
- **It executes with the run's netcup credential:** the step runs after the device-flow step exported `NETCUP_SCP_ACCESS_TOKEN` / `NETCUP_SCP_REFRESH_TOKEN_FILE`, so the binary holds the same plan/apply authority as the registry build would — but it is not a build the lock vouches for.
- **It is a stopgap, not a supply-chain change:** `required_providers` still names `rixlhq/netcup`, `tofu init` still runs without the override, and the step is deleted when upstream ships the fix. **Removal order matters:** delete the step first, then the release, then the fork branch — deleting the release first fails every apply closed at the download.
- **Not a boundary:** the digest pin authenticates bytes against the release, not against the source tree; whoever controls that fork release controls both. Treat the provenance as source-auditable, build-not-reproduced-by-CI.

Pinned by `tests/provider-stopgap` (structure via a YAML parse, plus a behavioural leg that executes the step's run block against a stub download and requires a digest mismatch to abort).

There are **no other standing credentials** in the module surface: no SSH keys, no Teleport tokens, no sockets. The standing credentials are the list-only witness key (row 1, optional, present only when all six `RECORDING_WITNESS_*` secrets are set), the ntfy publish token (row 2, pre-existing Gatus alerting, reused by the witness and the dynamic status-page puller when enabled — no new credential class; the puller env file is a second 0600 on-disk copy of the same token), the CloudFront origin secret (row 3, a shared auth header rendered only when the `:443` dashboard block is active; admission also requires an admitted TCP peer, never a header-derived client IP), and the interim Cloudflare AOP CA bundle (row 4, public cert material, retired at the A2 cutover). The default template carries none of them. GitHub falls back to repository-level values for any name a tenant environment does not define, so a managed run reads rows 1, 2 and 4 from its own environment and the ungated banner job refuses a managed dispatch while any of those names is defined at repository or organization level (issue #204, superseding #198's blanking; pinned by `tests/managed-operator-plane` — a drift guard over the committed workflow text, not a boundary: the isolation is GitHub's environment/secret scoping plus the workflow text on the executed ref); row 3 and `MAIN_BOX_IPV4` are the platform-plane values every anchor shares. Rows 3–4 are A2-era: row 3 ships with the edge buildout (the same run also consumes `MAIN_BOX_IPV4` — the main-box address exempt from the header gate, an address, already a secret for the firewall variable path, not a credential); row 4 is the interim pre-CloudFront edge authentication, retired at the cutover.

**Where the GitHub copies live (issue #204).** Rows 1, 2 and 4 keep their copy on the anchor's GitHub environment — the same scope as the rotate cell in the same row: the anchor's own environment on a managed anchor, and the `anchor` environment first, then repository level, for the operator's own runs (no `tenant`). The banner job refuses every managed dispatch while any of those names is also defined at repository or organization level, so one anchor's witness key, ntfy token or CA bundle never falls through to another anchor's run. Row 3 (`CLOUDFRONT_ORIGIN_SECRET`, with `MAIN_BOX_IPV4`) is the deliberate exception: a shared repository-level value for every anchor, and the banner does not refuse it.

## CI-side DNS-write credentials (retired in b3b)

Anchor DNS no longer has a runner-side provider credential. The `anchor-dns` job (`.github/workflows/provision.yml` → `.github/scripts/lib/broker-dns.sh`) mints a per-run GitHub OIDC token and calls the pc-control broker (`https://broker.piercloud.net`); the broker authorizes from the registry, cross-checks the IPv4 against the same-run report, performs the provider write plus the verify-after-write itself, and audits the result. No DNS provider token exists in the repo or on the runner, and there is no DNS credential here to rotate.

The A2 interim tokens below were the pre-b3b mechanism; the custody record stays for the retirement. No workflow consumes them anymore, but they must still be **deleted from org secrets** — deletion needs org admin scopes an automation token does not carry, so it is an owner step: `gh secret delete CLOUDFLARE_DNS_TOKEN --org piercloud-net` and `gh secret delete GCORE_DNS_TOKEN --org piercloud-net` (or expire/rotate them at the provider). Until deleted they remain readable by any workflow in any repository in the org — deletion is the control, not visibility:

| Secret (org-level, all repositories) | Pre-b3b scope | Retirement (b3b, #189) |
|---|---|---|
| `CLOUDFLARE_DNS_TOKEN` | `DNS:Edit` + `Zone:Read` on the `piercloud.net` zone only (Cloudflare tokens cannot be scoped below a zone) | No workflow consumes it; pending owner deletion of the org secret |
| `GCORE_DNS_TOKEN` | **No zone scoping** — Gcore tokens are account-wide: while the org secret exists, any workflow in the org that references it (a repo-write actor could add the reference) reads near-account-wide DNS write authority over the **dedicated platform account** | No workflow consumes it; pending owner deletion of the org secret |

The invariants the retired writer enforced (mask-first, token via a mode-0600 header file, `curl` + `jq` only, fail-closed without the active provider's token, verify-after-write before any thumbprint) are now the broker's own contract for the provider leg. The runner-side invariants that remain are the OIDC mint and the 0600 token/body files; registry authorization, the report cross-check and verify-after-write are broker-side. The M1 broker cutover for DNS completes when the two org secrets are deleted — no workflow consumes an org-level DNS-write credential anymore (the repo variables `NET_DNS_PROVIDER`/`STATUS_EDGE_DOMAIN` are deleted with the b3b merge and read back absent).

## Why the witness key is acceptable

- The anchor is deliberately the weakest box: unencrypted, always-on, cheapest class, different jurisdiction. Its existing job already requires it to be reachable and to hold an unlock key (tang). The witness adds metadata visibility, not access: the anchor still holds **no credential that reaches the main box**, and the witness key reaches nothing outside the operator's own DR bucket.
- The witness must never be able to read content — that is the security property, not a convenience: completeness is verifiable from listing alone, and the negative checks are part of the live acceptance (`scripts/030-recording-pipeline.sh` in `pc-admin` proves the key can list but cannot `GET`/`HEAD`).
- Honest residual: the witness runs on an operator-owned box, so the completeness claim is self-accountability until the CC-phase external manifest leg; a pre-SNP host-root attacker can also forge completion records. The arm's-length property being bought here is *detection* of pipeline suppression, not prevention.
