# DR runbook + boot-failure decision tree

Steady-state operations for your tang anchor: what breaks, how you notice, and what to do — all runnable from any browser, phone included. No plans or roadmaps here; this page covers the anchor you already run.

Related: [usage.md](usage.md) (end-to-end flow) · [invariants.md](invariants.md) (S1 / C-A review blockers).

Every `mode=apply` in this file is a managed dispatch (`tenant` + `anchor_ref` inputs): a tenant-less or ref-less apply is refused in the banner job before any gate or device card (b3b, #189).

## T0 / T1 / T2 — emergency-unlock ladder (advise, never mandate)

- **T0 baseline (shipped with this template):** LUKS passphrase keyslot in your password manager (PM) + dropbear-initramfs paste on the main box + public-repo break-glass card (provider → console-URL map). The passphrase stays in the PM — never on any service. The runbook "website" stores NOTHING.
- **T1 advised:** WireGuard peer in the main box initramfs (dropbear behind WG, no public initramfs port); Gatus must ALERT, not just monitor; PM emergency kit + recovery codes completed day-1, printed off-device (see the day-1 checklist below).
- **T2 opt-in:** BYO twin anchor — a second small box at a DIFFERENT provider, both user-owned, SSS t-of-2 via `extra_tang_urls`. The only availability upgrade that adds zero trust parties. Product default stays single anchor t:1 (see [usage.md](usage.md)).

## DR table

| Situation | Detection | Do | Do NOT |
|---|---|---|---|
| Anchor death (box down, tangd wedged) | Gatus ALERTs (T1); main box falls back to passphrase prompt at boot | Unlock with the passphrase keyslot; rebuild the anchor, re-bind or `regen` (same-URL fast path below) at your desk | Panic-migrate the main box anywhere |
| Shared platform unhealthy (`platform` row red) | Gatus `platform` row — monitor-only on tenant pages (no push; the operator anchor alerts on the same row) | Nothing on your side: the operator is already alerted. Red `your piercloud` + red `platform` = a platform problem; green `your piercloud` = your slice is fine | Rebuild or rebind your main box for a platform-side failure |
| Firewall policy deleted | Main-box canary (drift report planned — compare policies in the SCP until then) | Re-run [`provision.yml`](../.github/workflows/provision.yml) `mode=apply`; it re-converges the policy | Hand-edit policies in the SCP and forget them (drift returns) |
| Firewall drift (rule changed out-of-band) | Canary failure (+ `mode=check` drift report when live) | Same as above: dispatched re-apply | Assume the anchor is "just slow" — check the drift report first |
| Stale binding (main box moved, source IP changed) | Clevis fails after a move; canary carries the new IP | `mode=update-ip`: ADD the new IP first, confirm boot, then remove the old (ADD-before-move; operator requests, OWNER executes) | Remove the old IP before the new one boots (cutover lockout) |
| SCP outage (netcup control plane down) | SCP/API unreachable; anchor itself still answers clevis | **SCP outage: do NOT migrate hosts.** Wait it out — running anchors keep unlocking; nothing needs the API until you change something | Migrate hosts mid-outage (strands the moved box behind a stale rule with zero remediation) |
| Lost phone | You, noticing | Day-1 kit: recovery codes + root password in the PM emergency kit, printed off-device — recover GitHub/netcup access from any browser, then re-enroll | Keep all second factors on the one device (month-6 lesson — see checklist) |
| Device grant disabled (netcup turns off the OAuth device flow) | `mode=apply` fails at the approval step | STOP + open an issue in your tenant repo. Do not proceed. (C-A — no fallback of any kind is designed or permitted) | Invent a fallback: no one-run tokens, no pasted long-lived secrets, no "temporary" standing credential |
| Runner killed or run cancelled before teardown | The run stops mid-flight, so the `always()` teardown never runs — the device-grant refresh token can stay live up to ~30 days | Revoke your offline session for the tenant in netcup's Keycloak (SCP) admin/account UI, then re-dispatch `mode=apply` with the same managed inputs (`tenant` + `anchor_ref` — b3b requires them; a ref-less apply is refused before provisioning) | Assume the token died with the runner — only a teardown that actually ran revokes it |
| Dashboard cert stale (per-anchor cert nearing expiry, or an install that never served) | Gatus `dashboard TLS` endpoint fails its `[CERTIFICATE_EXPIRATION]` condition → ntfy ALERT when a push topic is set; ~30d warning window | Re-run the signing flow: fetch the on-box CSR, have the public single-SAN cert issued (interim: a public cert for the nested host from a CA the `status.piercloud.net` CAA authorizes — the operator path is `sectigo.com` (e.g. ZeroSSL); `letsencrypt.org` is authorized only for the broker ACME account (`accounturi` pin), so an operator LE account fails CAA; any other CA needs a CAA amendment first — pasted into the `ORIGIN_CA_CERT_PEM` variable as a leaf-first chain; broker ACME DNS-01 planned at M1), re-dispatch `mode=apply` (the run validates + installs in place + reloads Caddy). Rotation drill below. Tang is unaffected throughout (plain HTTP, separate port, zero TLS dependency) | Touch tang or the firewall to "fix" the dashboard; bind anything new while the dashboard is red |

`platform` is the shared infrastructure your server runs on — monitor-only on tenant pages (diagnosis, not a page). The operator's first check when it is red is the host watchdog state behind the endpoint (`/healthz` 503 = stale checks). While the fleet has one host, the row is that host; the aggregate meaning widens as hosts are added.

**Operator anchors:** the `platform` row alerts (tenant pages stay monitor-only). The role is the `ANCHOR_ROLE` variable (the anchor's own GitHub environment for a managed run, #204; the `anchor` environment, then repository level, only for the non-apply modes that still run unmanaged) — `operator` alerts, unset/`tenant` is monitor-only, anything else fails the run closed. After setting it (with a real `NTFY_TOPIC`), re-dispatch `mode=apply` (a managed dispatch with `tenant` + `anchor_ref`) and check the run log's `Gatus alert stanzas:` line: on the legacy shape it names `platform`; on a puller anchor (`STATUS_PULLER` set) the config render owns only `dashboard TLS (via edge)` and the platform alert stanza is seeded/rendered in the puller fragment — verify it with `grep -A2 'name: platform' /etc/gatus/tenant-endpoints.yaml` (an unset role silently downgrades the row to monitor-only). A run that clears the variable for a tenant-shape proof must restore it and re-dispatch to confirm the operator shape.

## Dynamic status-page endpoints (puller, issue #186)

On a slice-managed anchor (`STATUS_PULLER` variable set: the `anchor` environment, then repository level, for an operator run; the anchor's own environment for a managed run) the Gatus monitor rows stop being a dispatch-time constant:

- `010` renders only the two anchor-local rows (`tang (via Caddy)`, `dashboard TLS (via edge)`, both under `group: anchor`) into `/etc/gatus/config.yaml` — with the fragment's `platform` / `<alias>` groups, a puller-anchor dashboard has no "No Group" section; every watched HTTP row (`platform`, `your piercloud`, `private (gate)`, the derived `shared (gate)` while a `type: shared` site exists, the `public edge` row when the platform manifest sets `edge: true`, platform `hosts[]`, public tenant rows) lives in the puller-owned fragment `/etc/gatus/tenant-endpoints.yaml` (single-owner rule). **Group is part of the endpoint key** — adding `group: anchor` restarts these two rows' stored history once (both shapes; one row each). The seeded `your piercloud` and `private (gate)` rows stay red by design until the slice health endpoint and the Teleport buildout land; the retired `main` homepage row is replaced by `your piercloud`. Alert classes: the slice, gate and platform rows use the class-5 ntfy-JSON bridge (5/3, night emergency); public tenant rows are class 4 (native ntfy, priority 4, no resolve message). Gatus runs in directory mode (`-e GATUS_CONFIG_PATH=/config`, `-v /etc/gatus:/config:ro`); the mount-shape guard recreates a legacy file-mount container once at the cutover.
- `piercloud-gatus-pull.timer` (every ~10 min, jitter, `flock`) fetches the tenant manifest (`https://meta-<alias>.piercloud.site/.well-known/pc-status.json`) and the platform manifest (`https://platform.piercloud.net/.well-known/pc-status.json`), validates them (caps, names, allowlist, resolution guard, site classes: required `type`, namespace cross-check), parses the candidate fragment before installing it, writes atomically, and keeps `.last-good`.
- Acceptance is the local statuses API key set (`http://127.0.0.1:8080/api/v1/endpoints/statuses`) within ~90 s: a candidate that does not appear is rolled back to `.last-good` and pushed as a notice (under `skip-invalid-config-update` Gatus silently keeps the old config, so the key-set check is the acceptance).
- Failure ladder: 404/410 = not published (no counter, last-known-good held); 5xx/TLS/parse/validation counted per channel; 1–2 log only, ≥3 one ntfy notice plus a recovery message; removals are notified by name. State (`/var/lib/piercloud/gatus-pull.state`: last success, ETags, rendered hash) is printed at each dispatch. A candidate that fails the strict grammar or collides with `config.yaml` is counted per channel the same way (last-known-good held, no write) — not a fatal uncounted exit.
- Fetch bounds and the disclosed residual: HTTPS only, no redirects, bounded time/size, per-manifest host allowlists, and every accepted host resolved once and rejected when it resolves to a non-public address (loopback/private/link-local/metadata/ULA). Residual: a resolve-once check cannot fully close DNS rebinding — a name can resolve public at pull time and private at probe time; entry URLs stay inside the anchor's own domains, so the reachable target set is the platform's own DNS. The curl header file is read with a 16 KiB cap and the fetch deadline bounds it either way.
- The switch: `STATUS_PULLER` unset = legacy shape (no puller, `platform`/`main` + `GATUS_ENDPOINTS` in `config.yaml`; module consumers unchanged, the template/static-lane apply is retired by b3b). On the first puller-enabled dispatch `010` drops the `GATUS_ENDPOINTS` pairs with a loud dispatch-time log (D10) and seeds the fragment; move the wanted targets into the manifest and delete the secret. Turning the switch off removes the puller artifacts and the fragment so the legacy render can own the rows again.
- Boundary: the puller writes only the fragment (plus `.last-good`); `#51` may replace `config.yaml` only; `010` never removes unknown `*.yaml`. The scoped invariant-2 amendment is in [invariants.md](invariants.md); the ntfy token's second 0600 on-disk copy is inventoried in [security-posture.md](security-posture.md).
- `external-watch.yml` adds the D6 checks when the switch is set: each manifest HTTP 200 (404/410 = not published, skipped; last-known-good held) + `generated_at` ≤ 24 h, and every manifest entry (plus the seeded `platform` / gate / `your piercloud` rows and the derived `shared (gate)` / `public edge` rows) present in the dashboard's public endpoint keys — a changed manifest that never reached Gatus means a dead puller timer or a frozen fragment. The check appends to (never clobbers) a probe failure, and skips the key-set diff when the statuses-API snapshot was not fetched. On a managed anchor the switch lives in its environment, which the scheduled watch cannot read (its jobs select no `environment:`; tenant environments are also expected to deploy from `v*` tags only): the watch reads the `:puller` flag from the repository variable `EXTERNAL_WATCH_TENANTS` instead (#207), one leg and one incident per listed tenant. Switching the list on or off does not move an open incident: an open legacy-titled incident (`[external-watch] dashboard probe failing: …`) is no longer looked up once the list is set, and tenant incidents are no longer looked up once it is cleared, so close the old incidents by hand at the switch. The same holds per alias: removing or renaming an alias leaves its `[external-watch] <alias>: …` incident open with no leg to close it. A refused list falls back to the legacy single target and opens one `[external-watch] watch config refused: …` incident (with an ntfy push; the reason names the entry position and rule, never its text) that closes when the list parses again; while it is refused, tenant incidents are neither updated nor closed.
- **Site classes + derived rows (D13, issue #193):** every tenant entry carries a required `type` — `public` (`<site>-<alias>.piercloud.site`), `shared`/`private` (a site under `<alias>.piercloud.net`); a class/namespace mismatch rejects the whole manifest (fail-closed to `.last-good`). `shared (gate)` is derived (strict `[STATUS] == 200` at `https://id.<alias>.piercloud.net/login`, class 5) and disappears — with the removal notice — when the last shared site leaves. The platform manifest's `edge: true` derives `public edge`; the target is anchor-pinned (`https://edge.piercloud.site/healthz`), monitor-only on tenant anchors, alerting on the operator anchor. The platform must serve that path through the public edge before enabling the flag (platform-side follow-up).

**Managed dispatches (account lane):** every run that mutates a managed netcup account must carry that account's `anchor_ref` (the opaque registry reference for the anchor's account) so all runs on the account serialize — the workflow's concurrency lane becomes `anchor-<ref>`. `mode=apply` is managed-dispatch-only since b3b (#189): the anchor DNS stage writes through the pc-control broker, which needs the lane binding and the same-run IPv4 report, so a ref-less or tenant-less apply is refused at the preflight before any provisioning. A **tenant-less**, ref-less `update-ip`/`destroy` (neither touches anchor DNS) still falls back to the repo-wide static lane — which can overlap a managed run on the same account — and emits a loud warning (a tenant-set dispatch without a ref fails closed in every mode). A managed dispatch also selects its tenant environment via the `tenant` input; the environment must carry the `MANAGED_TENANT` marker equal to its name (set by the platform env lifecycle), or the run fails closed before the device card.

## Boot-failure decision tree (main box asks for a passphrase)

Your main box dropped to a passphrase prompt instead of unlocking via the anchor. Four causes, in order:

1. **Is the anchor up?** Check Gatus from the anchor's SCP console (`curl -s localhost:8080 | head -5` — HTTP 200 = alive). No → anchor death: type the passphrase (T0), then rebuild at your desk (same-URL `regen` below). Yes → step 2.
2. **Did anything firewall-shaped change?** Diff the firewall policies in the SCP (`mode=check` drift report planned). Drift or a deleted policy → `mode=apply` re-converges it, reboot, done. Clean → step 3.
3. **Did the main box move (new IP)?** Stale binding: the anchor only answers the IPs in the policy. `mode=update-ip` with ADD-before-move, confirm boot, then remove the old IP. No move → step 4.
4. **Was the anchor rebuilt or its tang keys rotated?** The binding points at keys that no longer exist: unlock with the passphrase, then unbind + re-bind (or `regen` on the same URL), verifying the new thumbprint out-of-band — never `-y` blind.

## Discovery fallback (multi-server accounts only)

Single-server accounts never need this. If a run aborts with `expected 1 server, found N`, set the `ANCHOR_IPV4` secret (the anchor's GitHub environment; a repository-level copy makes the banner refuse the managed dispatch) to the server-ready email's "IP address" verbatim (`203.0.113.10/22`-style suffix included; the run strips it) and re-dispatch. The value only selects among the addresses the resolved server itself reports (`GET /servers/{id}`): a value that matches none of them fails the run closed at the resolve step — SSH and the A record always carry an address the resolved server itself reports. (A value that selects *another* server in the same netcup account is closed only by the platform-side registry-IP cross-check, #132.) When the resolved server reports several IPv4s, a run with no explicit value fails loud with the address count — the addresses themselves are never printed to the public run log; read them in the netcup SCP and re-dispatch with one as `ANCHOR_IPV4`. Prefer renaming one box to `anchor-01-<you>` so discovery stays automatic.

## Same-URL rebuild = `regen` (2-minute DR)

Bind clevis to a DNS name (`anchor-01-<alias>.piercloud.net`, see `anchor_hostname`), never the raw IP. A rebuilt anchor at the same URL needs only `clevis luks regen -d <device> tang` — same URL, fresh keys, no unbind+bind ceremony.

## Caddy dashboard: edge checklist + cutover reversibility

Caddy (`caddy:2.11.4-alpine`, pinned + Renovate-watched) owns `:80`; `tangd.socket` listens on `127.0.0.1:8081`; Gatus stays loopback-only (`127.0.0.1:8080`, Caddy proxies the status host to it). The Caddyfile is dispatch-managed (same render pattern as the Gatus config): `handle /adv* + /rec*` → `127.0.0.1:8081` plain, NO redirect; `/.well-known/acme-challenge/*` → HTTP-01; the exact status hostname on `:443` (`https://<tenant>.status.piercloud.net`, rendered from TENANT_USER — `:80` has no dashboard handler) → `127.0.0.1:8080`; explicit per-tenant site blocks, NEVER `on_demand` TLS; catch-all aborts; the `:443` dashboard site also sends `Strict-Transport-Security: max-age=15552000` (no `includeSubDomains`), and `:80` no longer has any dashboard handler. Tang paths are never served on the `:443` dashboard vhost (they abort there). Caddy runs with host networking (its `127.0.0.1` dials reach tangd/Gatus on the host loopback; the netcup firewall stays the ingress gate). Monitoring note: Gatus probes tang only through Caddy's `:80` (a bridge-network container cannot dial tangd's `127.0.0.1`); tang-direct is proven every run by a host-level curl to `:8081/adv` before any proxy proof runs.

Operator edge ceremony (operator-plane, verified by eye after each change; the run's DNS writer is now the pc-control broker, scoped to the registered tenant names — the A + the explicit `<tenant>.status` CNAME — and cannot set zone-level records (the platform `*.status` wildcard, CAA) or edge settings (SSL mode, cache rules, WAF, AOP), so the edge ceremony stays outside the public repo — codification target: the private operator control plane). **Two TLS legs must both be up — they fail independently:**

- **Leg 1 — visitor → edge (A2: CloudFront).** *Live 2026-10-07: the CloudFront distribution (`E2VS7DMYXDGX8M`) + the platform wildcard + CAA exist; the anchor-side cutover (nested-SAN cert + origin auth) is the remaining step — until it lands the flat `status-<tenant>` name serves through the orange cloud.* The dashboard is the nested `<tenant>.status.piercloud.net`, covered by ONE platform wildcard `*.status.piercloud.net` (CNAME → the CloudFront distribution) + ONE ACM wildcard at the edge — no per-tenant edge cert — PLUS one explicit per-tenant CNAME `<tenant>.status.piercloud.net` → the distribution (written + verify-after-write'd by the anchor DNS writer). The explicit record is load-bearing on an RFC 4592-strict provider: the ACME DNS-01 challenge node `_acme-challenge.<tenant>.status…` makes the name an empty non-terminal and stops wildcard synthesis (Cloudflare masked this; Gcore does not — live 2026-10-07), so the name must answer directly. Cost: one record per tenant (Gcore is uncapped). The wildcard and the subdomain CAA (`issuewild "amazon.com"` for ACM + `issue "letsencrypt.org; accounturi=<broker account>"` + `issue "sectigo.com"`) are platform-level writes (Cloudflare today; re-created on Gcore at the `.net` zone move). Pre-cutover (anchor-side step pending): the flat `status-<tenant>.piercloud.net` name is served through the orange cloud (free Universal SSL covers the one label); **after the cutover the flat record may still resolve until B (the writer no longer maintains it), but the name no longer serves** (the rendered Caddyfile matches only the nested host; the old vhost is tombstoned — no redirect, no transition window).
- **Leg 2 — edge → origin (A2: CloudFront → anchor).** *Live 2026-10-07 (anchor-side cutover pending: nested-SAN cert + origin auth, PR #167).* CloudFront trusts **Mozilla-store CAs only**, so the anchor presents a **public single-SAN cert** for the viewer host `<tenant>.status.piercloud.net` (the SNI CloudFront sends and the Host it forwards; the anchor FQDN is only the origin `domainName` for resolution). The Cloudflare Origin CA is **dead for this leg**. Do NOT rely on Caddy auto-TLS (HTTP-01) for any proxied host (the nested dashboard included): Always-Use-HTTPS redirects the challenge to https, and the https follow-up needs the origin cert ACME is still trying to obtain — a catch-22 (live 2026-09-10, issue #88). Deploy a per-anchor pair (below); with a pair selected, a failed `:443` handshake fails the run closed — the WARNING variant applies only when no pair is selected (auto-TLS pending). **Cutover prerequisite (A2):** the first post-rename dispatch must carry the nested-SAN cert (the `ORIGIN_CA_CERT_PEM` variable, leaf-first chain) in the same run — the on-box pair is validated against `STATUS_HOST` before selection, so an old flat-SAN pair fails the run closed. Ordering note: the same dispatch applies the A2 firewall (tofu apply runs before the A1/010 step), so the flat name's Cloudflare→origin `:443` path is already cut at apply time — a failed dispatch leaves the dashboard down through both edges until a corrected re-dispatch (there is no old-name fallback window). The install gate also enforces the chain: a leaf-only value or a chain whose blocks are not each exactly one X.509 cert (no trailing DER) with a CA:TRUE, non-duplicate issuer per hop is refused (A2 — under the interim AOP path a single Origin CA cert is still accepted by design), and the run proves the public edge (HTTP 200 + dashboard marker + an explicit `x-cache: Miss` + CloudFront's `x-amz-cf-id`/`x-amz-cf-pop`/`via …cloudfront.net` header tuple — a response-forgery barrier, not cryptographic proof of the distribution; an absent or cached `x-cache` cannot prove the origin and fails the run, so keep the probe path uncacheable at the distribution) before reporting success.

- SSL/TLS mode **Full (Strict)** (edge → origin encrypted, origin cert verified).
- Cache Rule **Bypass** for `/.well-known/acme-challenge/*` (HTTP-01 must reach the box, never a cached edge hit).
- No WAF custom rule / Bot Fight Mode block on that path (challenge fetches look like bots).
- Zone-level **Authenticated Origin Pulls** with our own cert (interim Cloudflare-edge path; retired at the CloudFront cutover — CloudFront has no AOP, see the origin-auth bullet below; **A2 cutover step: delete `CF_AOP_CA_PEM` (`--env <tenant>`) before the cutover dispatch (the dispatch re-renders without AOP and flips `:443` off Cloudflare), then disable the CF zone setting after it — post-cutover the edge pull goes through CloudFront (which presents no Cloudflare AOP client cert) and Cloudflare is no longer admitted on `:443`, so an anchor still carrying the AOP bundle fails the probe** (out-of-order state, not a no-op: the run has already re-rendered `:443` under `require_and_verify` and reloaded Caddy, so every CloudFront origin pull 502s until the secret is deleted and a dispatch reruns — recover with `gh secret delete CF_AOP_CA_PEM --env <tenant>` + re-dispatch): mint a CA + leaf offline, upload the **leaf cert + key** to Cloudflare (zone-level AOP; global AOP's shared cert is publicly downloadable and adds ~no security), enable the setting, THEN set the `CF_AOP_CA_PEM` secret (**the CA bundle**, on the anchor's GitHub environment; a repository-level copy makes the banner refuse the managed dispatch) + re-dispatch — Caddy verifies the edge client cert at the handshake (`require_and_verify` + trust pool, 2.11.4), and the run itself asserts both halves (cert-less origin pull rejected; edge pull serves 200). Order matters: CF side first, origin second — the reverse black-holes every edge pull. Rollback, in this order: unset `CF_AOP_CA_PEM` + re-dispatch FIRST (the origin stops requiring the cert; edge pulls keep working while Cloudflare still presents it), then disable the CF setting (`102 --aop-disable`). The reverse order black-holes every edge pull until the redeploy. **DR rebuild note:** the provision job's AOP half asserts the *edge* pull, which needs the dashboard's edge record (the explicit per-tenant dashboard CNAME + the platform status wildcard, edge buildout) to exist — a rebuild dispatched while `CF_AOP_CA_PEM` is still planted fails the provision job before the platform records can converge (host does not resolve ⇒ curl exit 6; record still pointing at the dead old box ⇒ edge 521/522 / curl 22, reported with the trust-mismatch hint + this DNS caveat). Recover by `gh secret delete CF_AOP_CA_PEM --env <tenant>` + re-dispatch and let the platform records converge — do NOT re-enable AOP: the A2 cutover retires it for the `:443` origin leg (CloudFront has no AOP). A pre-A2 rollback to the Cloudflare edge is a code-level revert (the A2 firewall, gate and nested naming ship together) — not a `102` action. Until then, edge auth is firewall-allowlist + the `X-Piercloud-Origin` gate (documented degradation, dashboard-only).
- Per-anchor cert (issue #123, M2; A2 cert model): one per-anchor cert per box. The anchor generates its OWN key on the box (`/etc/caddy/origin-ca.key`, ECDSA P-256, **never leaves** — no key material ever travels through secrets or variables) and a CSR for the single SAN `<tenant>.status.piercloud.net`; the run publishes it as the `origin-ca-csr-<tenant>` artifact. Have it issued (interim: an operator-obtained **public** cert for the nested host from a CA the `status.piercloud.net` CAA authorizes — the operator path is `sectigo.com` (e.g. ZeroSSL); `letsencrypt.org` is authorized only for the broker ACME account (`accounturi` pin) — an operator LE account fails CAA; any other CA needs a CAA amendment first — pasted into the cert-only variable; the platform-broker ACME DNS-01 path — LE primary, ARI renewals exempt; ZeroSSL burst/failover; the anchor holds no DNS credential — is the M1 follow-up), then paste the **signed cert plus its issuer chain, leaf first** into the `ORIGIN_CA_CERT_PEM` **variable** (the anchor's GitHub environment; a repository-level copy makes the banner refuse the managed dispatch) (cert-only public material; the chain is required and enforced — CloudFront drops the connection with a 502 when the intermediate is missing, so a leaf-only value or a chain whose blocks are not each exactly one X.509 cert (no trailing DER) with a CA:TRUE, non-duplicate issuer per hop is refused before install) and re-dispatch: the run validates it fail-closed against the on-box key (public-key match, exactly one SAN equal to the status host, currently valid), writes it in place (the container bind-mounts the file, so the inode must survive; the run compares the container's view of the mounted PEMs to the rendered files and recreates Caddy when they diverge — a stale bind-mount inode is the live 2026-10-07 failure class), reloads Caddy and records the leaf fingerprint (the marker is the leaf's sha256, not the full-chain hash; it is a deploy marker, not proof); the run then proves the public edge (HTTP 200 + dashboard marker + an explicit `x-cache: Miss` + CloudFront's `x-amz-cf-id`/`x-amz-cf-pop`/`via …cloudfront.net` header tuple — a response-forgery barrier, not cryptographic proof of the distribution) before reporting success. The span/variable names stay `origin-ca` for continuity.
- Transition + one-way marker: a box that still carries the legacy shared wildcard pair (`/etc/caddy/origin.{crt,key}`) keeps serving it until the per-anchor pair has actually served on `:443`; that run drops the one-way `/etc/caddy/.origin-ca-active` marker, after which the legacy pair is **never selected again** — even if the per-anchor pair disappears, no silent resurrection (dashboard TLS stays pending until a per-anchor cert returns). After every dashboard is on its per-anchor cert (marker present, edge 200 under Full Strict), revoke the shared wildcard cert in the Cloudflare dashboard — LAST — and delete the retired pair secrets; the on-box legacy files are inert and can go with the usual disk cleanup.
- Rotation drill (manual, until `102 --rotate-origin`/`--revoke-origin` land): delete `/etc/caddy/origin-ca.key`, `.csr`, `.crt` and `.origin-ca.crt.sha256` on the box, re-dispatch `mode=apply` (a fresh key + CSR are minted; the one-way marker keeps the legacy pair suppressed, so the dashboard is briefly pending), sign the new CSR, set `ORIGIN_CA_CERT_PEM`, re-dispatch to install and serve, verify the edge 200, then revoke the previous cert at the issuing CA (interim: the CA that issued it; broker-side revocation at M1). Never regenerate the key in place while a cert exists — the state machine refuses it by design.
- Deployed cert material, NOT a standing API token: the box presents its origin cert but cannot rewrite the zone.
- CloudFront origin auth (A2, call D — edge buildout): **implemented (PR #167; `tests/edge-origin-auth/` pins the render text and `tests/bind-e2e` pins the adapted route order + a served peer/header matrix); the CloudFront leg is live (distribution `E2VS7DMYXDGX8M`, 2026-10-07) — the anchor-side cutover is the remaining step.** CloudFront has no AOP, so the origin leg is gated by the netcup firewall `:443` allowlist (the 81 published CloudFront origin-facing prefixes + the main-box `/32`) **and** a secret header enforced at Caddy (`X-Piercloud-Origin`; the main-box `/32` and loopback (`127.0.0.1/32`, `::1/128`) are exempt — the on-box probes connect from loopback; CloudFront overwrites any client-supplied value). The gate matches the raw TCP peer, never a header-derived client IP (the render carries no proxy-trust config). The gate lives **inside the dashboard catch-all `handle`** on purpose: Caddy adapts `abort` after `handle`, so a site-level gate would sit behind the catch-all and never run. Neither control alone meets the "anchor must not be world-open" constraint — together they do. **The first dispatch after the merge must be the cutover** (distribution + platform records live; nested-SAN cert + `CF_AOP_CA_PEM` deleted; `STATUS_PROBE_URL=https://<tenant>.status.piercloud.net/` set in the same window — the external watch otherwise keeps probing the tombstoned flat name) — the interim flat `status-<tenant>` name matches no site block once the new Caddyfile applies, and Cloudflare is no longer admitted on `:443`. (The formerly ungated `:80` exact-Host dashboard proxy was removed by the origin-hardening issue #225 (PR #226): `:80` now serves tang (`/adv*`, `/rec*`) + ACME only and aborts everything else — under auto-TLS Caddy's HTTP->HTTPS redirect answers the status host on `:80` instead, a redirect and never dashboard content — so no plain-HTTP dashboard front exists. The `:443` site also carries HSTS `max-age=15552000`.) The origin-range list is a synced, moving target (fail symptom = the Gatus edge row going red). **Origin mTLS (issue #202):** the distribution's `status-anchor` origin carries `OriginMtlsConfig` (ACM us-east-1 client certificate, EKU clientAuth) and each anchor runs `client_auth require_and_verify` against the committed `scripts/origin-mtls-ca.pem`; the shared `X-Piercloud-Origin` header is the transition control and is removed in the follow-up cutover. Roll back in the transition by reverting the anchor release (the header gate keeps the origin reachable) before touching the distribution. After the header is removed, reverting the release re-requires a header that CloudFront no longer sends, so a post-cutover rollback is a coordinated distribution-plus-anchor change: re-add the repository secret and the distribution's origin custom header first, then revert the anchor; never revert the anchor alone. The CA private key is in OpenBao `pki-origin` (sign-only role) with the break-glass copy in the operator secret store; a leaked key can mint clientAuth leaves the pool admits until the CA is rotated (a repo change plus one anchor dispatch), and there is no CRL.

Cutover reversibility (if Caddy ever wedges and the `:80` proxy with it — tang itself stays up on loopback throughout): on the box, `docker stop caddy`, remove `/etc/systemd/system/tangd.socket.d/listen.conf`, `systemctl daemon-reload`, `systemctl restart tangd.socket`, confirm `systemctl show tangd.socket -p Listen` answers `:80` again; then re-dispatch `mode=apply` to re-pin the firewall to the pre-Caddy shape. Dashboard stays down until Caddy returns — tang does not wait for it.

Bind-proof in CI (the keyboard problem): `tests/bind-e2e/` fronts a mock tang with the repo's real rendered Caddyfile and runs `clevis luks bind` + `unlock` through it on every PR touching `scripts/`, `main.tf`, workflows, or the harness — the Caddy-in-front path stays bind-proven without the tenant's keyboard.

## Rescue-chroot runbook (DR only)

Rescue boot is the last resort, not a workflow: the netcup rescue system disables the firewall entirely while it runs. After ANY rescue boot, rotate the tang keys afterwards (`--rotate` path, then re-bind / `regen`), because the disk was attached to a second system.
